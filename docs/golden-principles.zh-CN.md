# 黄金原则

这些带有明确倾向、可机械执行的规则，用来让这个由智能体生成的代码库
在未来的智能体运行中依然清晰、统一、易于理解。能由 CI 强制执行的规则
应尽量自动化；其余规则则通过约定遵守，并在评审中检查。某条规则一旦被
证明足够有价值，就应升级为 lint 规则（模式可参考 `tests/test_file_size.py`）。

## 边界
- **在边界处校验数据结构。** 在入口处解析并校验输入（frontmatter 通过
  `openkb/frontmatter.py`，配置通过 `openkb/config.py`）。绝不要建立在
  猜测的数据结构之上。

## 复用
- **优先使用共享工具，而不是手写辅助函数**，这样不变量才能集中维护。
  在编写新工具前，先检查 `openkb/` 中是否已经存在可复用的实现。

## I/O 与状态
- **所有 wiki 文件写入都必须经过 `openkb/locks.py` / `openkb/mutation.py`**
  （原子写入、崩溃安全）。不要对 wiki 目录树进行临时性的随意写入。
- **所有诊断信息都通过 `openkb/log.py` 记录**，不要直接使用裸 `print`。

## 规模与形状
<a id="file-size"></a>
- **模块应保持职责聚焦，且控制在 800 行以内**（由
  `tests/test_file_size.py` 强制执行）。大型模块应按职责拆分为更聚焦的
  单元。当前已超限的文件属于历史遗留，原因记录在该测试的
  `_GRANDFATHERED` 集合中，并额外追踪于
  `docs/internal/tech-debt.md` *(仅维护者本地可见，不纳入 git)*。

## 文档
- **`AGENTS.md` 是地图，不是手册。** 保持简短；更深入或更本地化的文档
  放在 `docs/`（公开）和 `docs/internal/`（仅维护者本地可见，不纳入 git）
  下。
